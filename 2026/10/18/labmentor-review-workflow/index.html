LabMentor 复盘归档：从多轮追问、冲突修复到部署

发表于 2026-10-18分类于 学习实践

昨天还在排查模型调用、准备配置后续节点，今天继续推进 LabMentor 的复盘归档流程。借助 Codex，我把重点放在信息怎样跨轮保留、用户撤回旧结论时怎样处理，以及生成内容到底处于什么状态上。晚间完成冲突修复和指定用例回归后，我部署了“v0.1.0-复盘草稿生成”版本，并确认部署成功。

这一天并不是把所有归档功能一次做完。已经完成的是复盘草稿生成流程的配置、指定场景验证和部署；知识库真实写入、入库凭证与部署后的接口调用，仍需要继续验证。

一、把信息提取、状态合并和内容生成分开

复盘归档接收的是学生对实验过程的描述。输入可能包含故障现象、操作过程、已确认根因和正确做法，也可能只有一句“这次放大电路调不出来”。流程必须先判断信息是否够用，再决定追问还是生成材料。

今天的工作流保持 12 个节点、12 条连线，主要过程是信息提取、复盘信息合并、记忆更新、缺项判断，再生成复盘报告、普通 Markdown 错因卡和 1～3 条迁移任务。迁移任务指把这次经验应用到相近问题上的练习或核验任务。

现象、操作、根因、核验依据、正确做法分别保存。后一轮没有提供某个字段时，需要保留前面的有效信息，不能因为一句简短补充就把整个记录覆盖掉。同时，“没有提到根因”和“明确不知道根因”要分别处理：前者需要询问，后者应保留“待核验”，不能为了让报告看起来完整而补出一个答案。

二、正常路径通过后，撤回旧结论暴露了问题

下午先验证了完整输入和两轮补充。晚间提交前，我又要求核对当前模型绑定，并检查前后信息冲突的情况。

这次发现了一个更具体的问题：用户撤回此前认定的根因、提出另一种怀疑后，旧根因仍可能被沿用。修复前的记录中，冲突列表为空，流程没有进入追问分支，反而继续生成内容。仅看到运行节点全绿，不能说明这个业务场景处理正确。

随后修复集中在信息提取和合并两个节点。增加明确的撤回标志和候选原因字段；检测到撤回后，把旧根因及依据移入历史，清空当前结论和依据，撤销确认标志，将状态改为待核验，并强制追问。新的怀疑只是候选原因，不能直接替换成确定根因。

修复后的配置在 22:26:20 保存。最终撤回场景中，冲突记录不再为空，三个内容生成节点没有执行，流程停在需要澄清的位置。这样既留下原来的判断过程，也避免把已经被撤回的说法继续写进报告。

三、用最终回归记录判断这一版做到哪里

下面记录的是修复后的实际平台调试结果，时间均为北京时间。耗时只描述这几次运行，不代表平均性能或准确率。

  • R1 完整记录：22:30 开始，调试耗时 45.92 秒，生成五段复盘报告、Markdown 错因卡和 3 条迁移任务，状态为已生成、草稿未入库。
  • 同一会话撤回根因：22:33 开始，耗时 3.49 秒，旧结论及依据进入历史，确认标志撤销，转为待核验并追问，没有继续生成三类材料。
  • R2 缺项首轮：22:35 开始，耗时 1.64 秒，针对缺失内容询问，没有自行推断元件损坏，也没有误判为撤回。
  • R2 同会话补充：22:36 开始，耗时 31.80 秒，保留首轮现象，合并补充信息，未知根因仍标为待核验，生成报告、待审核卡片和 3 条安全核验任务。

下午和修复前的运行保留为历史记录，验收采用上面这组最终回归。完整输入、缺项输入与撤回输入分别检查，才看得出分支是否真正按要求工作。

这里还有一个边界：学生报告自己确认过某个原因，不等于教师已经审核；指定四轮通过，也不能外推成所有表述方式都能正确处理。后续在补充有效依据后解除冲突的自然语言平台回归，还需要继续做。

四、模型显示名称和实际调用标识分别核对

今天我要求工作流使用自己接入的 DeepSeek 服务。最终核对了四个 LLM 节点的服务绑定、实际调用配置和接口来源，确认本次工作流使用的是预期的自定义服务。具体接口地址和接入配置不在公开文章中展示。

这次记录把服务显示名称、实际模型标识和接口来源分开，避免只看一个列表名称就下结论。上述结果对应本次工作流配置核对，不代表对其他模型版本或能力作出比较，也没有把界面名称当作厂商正式版本证明。

五、把“生成”和“入库”写进规格与交接

复盘归档的持久化方案也作了修订：移除“新建独立错题本库加原生 FAQ”的假设，保留普通 Markdown 错因卡，审核后导入现有综合库作为候选方案，并明确标记待验证。

规格区分四种状态：已生成、待导入、已入库、写入失败。没有成功写入凭证，就不能显示“已归档”。这也意味着生成出一张错因卡，只完成了内容准备的一步。

交接材料包含修订后的规格、持久化决议草案、R1/R2 用例、归档失败用例，以及实际平台运行记录。失败用例在本地测试副本中模拟，检查失败时是否保留报告和卡片、是否明确提示失败，以及能否手动导出。该组本地检查共 14 项通过，但没有执行真实知识库写入，不能代替平台失败测试。

最后整理了交接压缩包和追加原 PR 的提交提示词。材料已经准备好，仓库提交本身仍需按提示词执行并核对结果，不能把打包完成写成已经推送。原来的复盘归档事项仍保持开放，持久化决议也没有提前标为完成。

六、部署完成后仍要补上的验证

22:55，我确认“v0.1.0-复盘草稿生成”部署成功。这个版本名称对应当前已验证范围：生成草稿、缺项追问和撤回冲突处理。

部署成功以后，还需要继续验证：

  • 实际调用部署后的入口，核对输入、输出和运行版本。
  • 确认综合知识库的导入入口、权限和格式，完成必要审核。
  • 在获准的测试库或副本中验证真实写入失败、内容保留和手动导出。
  • 成功导入后保留文档标识、内容版本、时间和成功结果等凭证，再验证新会话检索及隔离情况。

今天另外询问了 Windows 上边读英文 PDF 边翻译的开源工具。安装配置和实际阅读体验尚未形成可记录的结果，后续使用后再补充。

这次实践留下的具体经验，是把验收落在状态变化和分支行为上：能输出不等于输出依据正确，撤回旧结论后是否停止生成，比运行面板是否全绿更值得检查。下一步继续沿着现有记录验证部署后的调用与真实入库，把尚未确认的部分逐项补齐。
