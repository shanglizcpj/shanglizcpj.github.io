Rust 练习达到 110/110，接着追问程序怎样运行

发表于 2026-11-15分类于 学习实践

本文记录截至当日 22:00（北京时间）的情况，后续进展见之后的日志。

今天有一个明确的阶段性结果：我的 Rust 练习仓库完成了新的算法和综合练习提交，课程检查达到 110/110，成绩上传接口也返回接受。

与此同时，我还在问一些很基础的问题：“BFS 是队列吗？”“DS:SI 是什么东西？”把这些问题和通过记录放在一起，反而能更准确地描述今天的进展：代码通过了这一轮检查，理解仍需要沿着具体执行过程继续展开。

前几天记录的链表、冒泡排序和二叉搜索树，主要还是读代码与推演。今天的不同之处，是仓库中出现了相应改动，并且有新的实际检查结果。

二、“BFS 是队列吗？”先分清算法和工具

17:37，我问了“BFS 是队列吗”，随后要求具体展示。这是一个适合继续追下去的问题：BFS 是一种遍历方式，队列是实现这种遍历时常用的数据结构，两者不能直接画等号。

FIFO 队列让较早发现的节点先被处理。对于无权图，从起点逐层扩展时，它能让较近的一层先于更远的一层展开。图中还需要记录节点是否已经发现，避免沿不同边重复安排同一个节点。Cornell：图遍历课程讲义

下面是整理笔记时补的一个小推演，不是当天保存的程序运行输出。假设 A 连向 B、C，B 和 C 都连向 D，并按 B、C 的顺序检查 A 的邻居：

初始：            [A]
取出 A，加入 B、C：[B, C]
取出 B，加入 D：  [C, D]
取出 C，D 已发现：[D]
取出 D：          []

访问次序是 A、B、C、D。关键不只是使用了一个名叫“队列”的容器，而是每一步都遵守“从队头取出，把新发现的节点加入队尾”的顺序，并在加入时标记已发现。

这样再回看代码，就可以分别检查三个问题：当前处理哪个节点，哪些节点还在等待，哪些节点已经安排过。比把 BFS 和队列当成同一个概念，更容易对应到具体实现。

三、开始读操作系统启动代码

傍晚，我询问了操作系统理论的学习方法和 B 站课程。之后又带着一张引导程序课件截图继续提问，问题落到了 DS:SI 这样的具体记法上。

这里先把两个层次分开：课程和教材的比较属于选路，读一小段引导程序则是在理解执行细节。目前没有确认最终选定哪套课程，也没有把助手提出的学习周期当成我已经决定执行的计划。

在这类 16 位 x86 代码的上下文里，DS:SI 不是一个单独的寄存器，而是把段寄存器 DS 与偏移寄存器 SI 放在一起表达内存位置。以字符串搬移指令为例，16 位地址形式通常用 DS:SI 指向源位置，用 ES:DI 指向目标位置。读这类代码时，要同时追踪“从哪里取”和“向哪里写”，不能只看某一个寄存器的数值。Intel 指令手册：MOVS 系列

这部分仍停留在课件阅读与提问，尚无自己的引导程序编译、模拟器启动或内核运行记录；老式引导代码也不能直接等同于现代电脑完整的启动流程。

四、数据库实验：失败同样需要写清适用条件

今天凌晨还留下了一组新的 MiniVectorDB 内存边界实验记录。它针对的是保留旧排序路径的指定镜像，不能直接代表当前代码版本。

三组实验都使用 300,000 行数据，将内存限制设为 24 MiB，并禁用 swap。查询按 id 倒序取大结果集，LIMIT 分别为 300000、150000、300000。三组目标查询均退出 137，容器记录 OOMKilled=true，没有返回响应数据；内核日志也记录了对应的内存限制触发杀进程事件。

这比单独看到“进程退出”更能支持内存耗尽的判断。第一轮的原始日志还显示，装载、崩溃恢复和前置校验通过了，失败发生在之后的大结果排序查询。因此，前面的校验通过，不等于所有查询都能在同样的内存限制下运行。

这组记录能说明旧镜像在这些条件下失败，不能单凭三个失败样本确定通用内存下限，也不能证明当前版本存在相同问题。关于后续修复、推送和其他收益的描述，还需要与对应版本及原始日志对齐，暂不并入这里的已验证结果。

今天的收获与下一步

今天的记录可以分成三个层次：Rust 有新的代码提交和课程通过结果；BFS 与操作系统启动还有具体概念需要继续解释；数据库则留下了带明确条件的失败样本。

下一步值得做的小练习，是不看讲解重新画出 BFS 的队列变化，再对着引导程序标出源地址、目标地址和寄存器的用途。这是后续练习建议，不是今天已经完成的内容。先把检查结果、阅读过程和待验证问题分别记清楚，才能知道下一次真正推进了哪一步。
