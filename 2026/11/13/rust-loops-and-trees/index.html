从冒泡排序到二叉搜索树：看清循环边界与节点关系

发表于 2026-11-13分类于 学习实践

本文记录截至当日 22:00（北京时间）的情况，后续进展见之后的日志。

昨天主要看链表合并，今天继续读 Rust 算法代码。上午的两个问题分别是：冒泡排序里的两层 for 怎样配合，去掉 .rev() 会怎样；二叉搜索树如何用 Option 和 Box 表达节点关系，并完成插入与查找。

这两段代码都来自我发出的讲解请求。下面按代码做推演，再记录本地模型测速和资料整理的进展，暂不把阅读代码写成已经完成练习。

一、冒泡排序里的 .rev() 影响什么

今天讨论的实现是：

fn sort<T: Ord>(array: &mut [T]) {
    for end in (1..array.len()).rev() {
        let mut swapped = false;

        for i in 0..end {
            if array[i] > array[i + 1] {
                array.swap(i, i + 1);
                swapped = true;
            }
        }

        if !swapped {
            break;
        }
    }
}

两层循环分别负责什么

假设数组长度为 5，外层的 end 依次是 4、3、2、1。内层 0..end 不包含 end，所以当 end = 4 时，比较的下标对是：

(0, 1) → (1, 2) → (2, 3) → (3, 4)

每次遇到左边比右边大的元素就交换。这样走完一轮，当前范围内的最大元素被推到 end 位置。下一轮把右边界缩小，就不必重新处理已经归位的部分。

这里可以记住一个检查点：每轮结束后，右侧已经确定的有序部分扩大了一格。 外层倒序缩小范围，正好配合内层从左向右的比较方向。

直接去掉 .rev() 会出错

我接着问：“如果不用这个 rev 有关系吗？”

可以用 [2, 3, 1] 手动推演。去掉 .rev() 后，第一轮 end = 1，只比较 2 和 3，没有交换，于是 swapped 仍为 false，程序立即退出。但最后的 1 还没处理，数组显然没有排好。

即使暂时不考虑提前退出，范围从小到大也不符合这段冒泡过程的安排。例如 [3, 2, 1] 在第一轮变成 [2, 3, 1]，第二轮结束只得到 [2, 1, 3]，仍然无序。

所以，修改循环方向时，需要同时检查比较方向、每轮处理范围以及提前结束条件。不能只把 .rev() 当成一个可随手删除的写法。

原实现里，只有在完整扫过当前待处理区间、确认没有交换时，才可以提前结束。空数组和单元素数组的外层范围为空，也就不会进入相邻元素比较。

二、二叉搜索树：拥有节点与借用节点

随后我贴出一份二叉搜索树代码，请求解释。它的节点结构是：

struct TreeNode<T: Ord> {
    value: T,
    left: Option<Box<TreeNode<T>>>,
    right: Option<Box<TreeNode<T>>>,
}

Option 表达子节点是否存在，Box 持有堆上的节点，使递归结构能够通过间接引用表示。整棵树的根同样是 Option<Box<TreeNode<T>>>，None 表示空树。

这与昨天直接操作 NonNull 的链表写法不同。今天这份树结构通过 Box 持有节点，通过普通借用访问或修改，代码不需要显式的 unsafe 块。

插入：选择一个子树位置继续处理

节点的插入逻辑先比较新值与当前值：

let child = match value.cmp(&self.value) {
    Ordering::Less => &mut self.left,
    Ordering::Greater => &mut self.right,
    Ordering::Equal => return,
};

小于当前值就选择左边，大于就选择右边，相等则直接返回，因此这份实现不保存重复值。

这里的 child 指向的是左、右子树中的一个存储位置，类型为 &mut Option<Box<TreeNode<T>>>。后面遇到 Some(node) 就递归插入；遇到 None，通过 *child = Some(...) 把新节点放进那个位置。

按代码中的插入顺序 5、3、7、2、4 推演，树形为：

    5
   / \
  3   7
 / \
2   4

它保持了二叉搜索树的大小关系，但没有自动平衡的步骤。插入和查找都沿树高前进；树较平衡时路径较短，退化成单链时，最坏仍要经过线性数量的节点。

查找：移动的是观察位置

查找函数从下面这句开始：

let mut current = self.root.as_deref();

在这里，as_deref() 把对 Option<Box<TreeNode<T>>> 的借用转换为 Option<&TreeNode<T>>，得到节点的共享引用，原来的 Box 仍留在树里。Option::as_mut() 则提供内容的可变借用，用在插入等需要修改结构的地方。Option 官方文档

之后的 while let Some(node) = current 每次查看一个节点：目标值较小就转向左子树，较大就转向右子树，相等就返回 true。走到空位置时循环结束，返回 false。

current 可以重新赋值，不代表正在修改树。它只是把“下一次查看哪里”从一个共享引用换成另一个共享引用。

代码附带两个测试函数，覆盖空树查找、插入后查找、缺失值以及重复插入。不过，测试写在代码中和测试实际通过是两件事。目前没有核到当天这两道算法练习的执行输出，因此这里保留代码分析，不写完成数量或新评分。

四、口述史材料：先分清来源，再组织报告

晚上，我把教师采访、校史剧《选择》的演员材料和公开发言放到一起，请 ChatGPT 准备后续使用的 Codex 提示词，并明确将采访全文与采访问题收入报告附录。

当天形成的是提示词和资料任务包，包内有来源文件、说明及文件清单，尚未看到报告成品。八份核心材料需要先分为五份教师访谈、两份演员讲述和一份公开发言。

其中有两个容易混淆的地方：

  • 扮演历史人物的演员在谈角色塑造和排练，这些内容属于演员的经历，不能当成历史人物本人接受采访。
  • 演出后的公开讲话应标注为公开发言，不能改写成针对本次实践的专访问答。

此外，材料中还保留了待核文字、编辑说明和没有完整回答的问题。整理时应让这些标记继续可见，不能为了让文章连贯而补出不存在的答案。上传和整理文件的日期，也不等于实际采访日期。
