Rust 线程与宏：共享状态、等待完成和作用域

发表于 2026-11-10分类于 学习实践

昨天整理智能指针时，我关注的是“多个变量共享了哪一份数据”。今天继续看 Rustlings 的线程练习，问题变得更具体：spawn 怎样创建线程，多个线程怎样修改同一个计数，以及 join() 究竟在等待什么。

下午看宏时，我又问了两个问题：“为什么 my_macro 要加 !？”“宏一定要先声明才能调用吗？”这篇笔记结合当天提交和自动检查记录，把这些问题放回实际代码中说明。

一、创建线程和等待线程，是两步操作

thread::spawn 创建线程，并返回一个 JoinHandle。保存句柄，是为了之后能够等待对应线程结束、取得返回值。把句柄放进向量，并不是启动线程的动作；线程创建后就可以被调度执行。标准库文档区分了这两个环节。

当天的 threads1.rs 提交补上了：

results.push(handle.join().unwrap());

这行代码先等待 handle 对应的线程完成，再把它返回的值存进 results。join() 返回的是 Result，这里用 unwrap() 取出正常完成时的结果；若线程发生 panic，这种写法也会触发 panic。

按向量顺序调用 join()，不代表工作线程也按照这个顺序完成。等待第一个句柄时，其他线程仍然可以继续运行。实际日志里，十个线程的完成信息就没有严格按照编号排列。参见线程提交和 JoinHandle::join 的说明。

二、共享所有权之后，还需要保护修改过程

我最初贴出的 threads2.rs 中，共享状态是：

let status = Arc::new(JobStatus { jobs_completed: 0 });

后面却调用了 status_shared.lock()。这里的类型是 Arc<JobStatus>，内部的 JobStatus 并没有提供 lock() 方法。

当天提交把状态改成了 Arc<Mutex<JobStatus>>，对应的关键代码如下：

let status = Arc::new(Mutex::new(JobStatus { jobs_completed: 0 }));

// 每创建一个线程，先克隆一个指向同一份状态的 Arc。
let status_shared = Arc::clone(&status);
let handle = thread::spawn(move || {
    thread::sleep(Duration::from_millis(250));
    let mut job_status = status_shared.lock().unwrap();
    job_status.jobs_completed += 1;
});

在这段代码中，Arc 负责共享所有权，Mutex 负责控制对共享数据的访问。Arc::clone 新增的是指向同一份状态的句柄，并没有复制一个独立的任务计数器。move 将这个句柄移入线程闭包。两者的职责可以分别对照 Arc 文档与 Mutex 文档。

lock() 成功后得到锁守卫，通过守卫修改计数。守卫离开作用域时释放锁。这道题把模拟耗时的 sleep 放在加锁之前，因此休眠期间不会占着这把锁。

练习在每次 join() 后打印共享计数。这次自动检查实际打印的是：

2, 2, 5, 5, 6, 6, 9, 9, 9, 10

这组数字值得单独留下：等待一个线程结束，只能确认这个线程已经完成；读计数时，其他线程可能也已经更新了共享状态。因此，中途读到的值可能重复，也可能跳过某些数字，不要求依次输出 1 到 10。

这只是本次运行的输出，重新运行时的中间序列可以不同。若十个线程都正常执行一次递增，并且全部成功 join，最终计数才有依据确定为 10。

三、通道里克隆的是发送端

threads3.rs 用通道接收两个生产线程发来的数据。当天修改在移动发送端到闭包之前，先克隆出第二个发送端 tx2，让两个线程各自持有可用的发送端。

这次检查最终收到 10 个数字，但两个线程的消息存在交错。日志中的接收顺序是：

1, 6, 7, 2, 3, 8, 9, 4, 10, 5

这里能够确认的是该次运行收到了预期数量的数据，不能把这组交错顺序当成每次运行都必须产生的结果。对应提交同时包含了线程等待、共享状态加锁和发送端克隆这三部分修改。

四、宏的调用标记和作用域，要分别看

macros1.rs 的改动很直接：把 my_macro() 改成 my_macro!()。! 表示这里使用宏调用语法，编译器会按照宏的规则展开代码。

但“宏是否一定要定义在前面”不能只用一句口诀概括。macro_rules! 宏有文本作用域，也可以通过导入或重新导出参与路径作用域。普通的、未导入的文本作用域宏，从定义之后开始可见；涉及 use 时，需要继续看名称是怎样被引入的。Rust Reference对此作了区分。

当天 macros2.rs 的实际解法没有把宏定义移到 main 前面，而是增加了 use my_macro;：

fn main() {
    my_macro!();
}

macro_rules! my_macro {
    () => {
        println!("Check out my macro!");
    };
}
use my_macro;

这个例子通过 use 引入宏名，因此不能仅凭“调用写在定义前面”就判断它一定失败。

macros3.rs 则保留了模块内的宏定义，在模块中增加 pub(crate) use my_macro;，然后从外面通过 macros::my_macro!() 调用。这里使用的是模块内重新导出，不是 #[macro_export]。

macros4.rs 的修改是在两个匹配分支之间补上分号。几道题分别检查调用语法、名称可见性和匹配规则的结构，遇到编译错误时也应该分开排查。宏练习提交保留了这些具体差异。

五、这次检查通过了哪些部分

11 月 10 日的两次提交分别更新了线程三题和宏四题。对应提交 2c88bfe 的自动检查逐项运行了 threads1–threads3、macros1–macros4，七项都显示运行成功、退出状态为 0。

整个仓库当次的结果是 90/110 道练习通过，仍有 20 道未通过。流程中的“Mark unfinished exercises”步骤因此失败，整次评分运行显示为 failure。七道题运行成功、总计通过 90 道练习和整条流程失败，需要分别记录，不能合并成“全部测试通过”。

本次核对时，主分支仍指向上述提交；这里记录的是该提交及其对应运行的结果，没有把旧日志直接当成未来版本的状态。完整依据见评分运行。

今天这组练习可以留下四个检查点：线程是否创建，是否等待了需要等待的线程，共享修改是否受到同步保护，宏名是否能在调用位置解析。把这几件事分开看，代码的修改依据和运行结果就更容易对应起来。
