链表合并与数据库实验：读懂代码，再看验证

发表于 2026-11-12分类于 学习实践

本文记录截至当日 22:00（北京时间）的情况，后续进展见之后的日志。

今天继续看 Rust 链表，也问了梯度下降、反向传播和数据库性能方面的问题。几个问题都很具体：as_ref().val 访问的是什么，为什么需要 unsafe，反向传播如何参与参数更新，以及相同引擎为什么会出现不同的运行耗时。

这篇记录先整理代码和概念，再回到 MiniVectorDB 当天留下的实现与测试日志。代码解释、候选实现、本地测试和平台结果，需要分别记清楚。

一、链表合并：先看指针，再看连接顺序

今天我贴出了一份链表练习和一段 merge 实现，请求逐步讲解。节点里有 val，以及类型为 Option<NonNull<Node<T>>> 的 next；链表保存头指针、尾指针和长度。

与逐个复制数值到新节点的写法不同，这段实现复用原来的节点，调整它们之间的连接。

as_ref().val 是两步操作

看到下面的比较时，我又问了 as_ref 和 val 的含义：

a_ptr.as_ref().val <= b_ptr.as_ref().val

这里的 a_ptr 是 NonNull<Node<T>>。调用它的 as_ref() 得到节点的共享引用，再通过 .val 访问节点中保存的值，比较的是两个值的大小。

昨天接触过 AsRef 这个借用转换 trait。今天虽然也出现了 as_ref，接收者却是 NonNull，调用的是它自身的方法。读代码时只认方法名还不够，要先确认左边对象的类型。

为什么这里需要 unsafe

NonNull 保证指针非空，但非空指针仍可能悬空。调用 as_ref() 前，还要保证指向的对象有效、已初始化、正确对齐，并满足引用的生命周期和别名规则；通过 as_mut() 修改节点时，也要满足可变引用的要求。标准库将这些方法标记为 unsafe，要求调用方保证指针能够合法转换为引用。NonNull 文档

因此，写上 unsafe { ... } 不会自动消除风险。继续检查这段链表时，需要追问：节点由谁分配、何时释放，合并过程中有没有别的引用仍在访问它，原链表和新链表最终由谁负责回收节点。

合并过程里，顺序很重要

这段代码的主要步骤是：

  1. 用 a、b 分别指向两条链表当前还没有处理的节点。
  2. 两边都有节点时，比较当前值，选出较小的节点。
  3. 先保存该节点原来的后继，让对应游标向后移动，再把选中节点的 next 断开。
  4. 把选中节点接到结果链表尾部，并更新尾指针。第一次加入节点时，同时设置头指针。
  5. 一条链表处理完后，把另一条的剩余部分接上，更新尾指针和总长度。

第三步尤其值得单独看：如果先清空 next，再试图沿它向后走，就会丢失后续节点的入口。维护头尾指针时，也必须照顾空链表的情况。

在两条输入链表都已排序、节点归属和指针有效性满足要求的前提下，这种合并方式最多依次处理两条链表中的节点，时间复杂度为 O(m+n)，不需要为每个元素重新分配节点。

目前这部分能确认的是代码阅读和提问，还没有可核对的当天提交或编译测试结果。空链表、重复值、全部元素落在同一侧等情况，以及节点释放逻辑，仍应放进后续检查。

二、反向传播负责求梯度，优化器决定怎样更新

神经网络方面，我从“梯度下降的作用”问起，接着问了 MSE、CE，以及反向传播是不是可以用来求梯度下降需要的偏导数。

可以先把一次训练中的职责分开：

  • 损失函数衡量预测与目标的差异。MSE 是均方误差，常见于回归；CE 是交叉熵，常见于分类。
  • 反向传播利用链式法则，计算损失对各层参数的梯度。
  • 优化器根据梯度及自身规则更新参数。普通梯度下降的形式是 θ ← θ − η∇L(θ)，其中 η 是学习率。

这样理解，“用反向传播求偏导”这个方向是对的，但求出梯度之后，还要由具体更新规则决定怎么走。学习率、数据和模型都会影响训练，损失在一次更新后是否下降，也需要看实际情况。

今天上传的另一张材料提到了权重空间编程：让大模型直接读取、修改另一个网络的权重。原作者把它描述为早期实验，其中一些任务不通过梯度下降进行权重编辑。Weight-Space Programming 原文

这给基础概念提供了一个对照：参数可以通过不同机制发生变化，评价效果仍要依靠明确的任务和实验。这部分目前是概念学习，没有自己的训练或复现实验结果，也不能据此判断反向传播已经失去价值。

三、数据库实验：没有通过的方案，也要留下结果

上午我问过一个性能问题：引擎源码完全一样，为什么运行速度能差这么多？随后又追问，新版代码是不是可能有多余内容。

单看代码长短，无法判断性能。比较版本时，至少要核对实际构建出的程序、输入数据、资源限制和运行方式，再看重复运行的分布。当天截图中的两组耗时报告还缺少与之对应的原始跑分日志，所以这里不直接据此排列版本优劣。

当天 MiniVectorDB 的本地文件则保留了另一轮较完整的实验过程。

自适应自旋没有通过验收

首先尝试的是标准输入等待相关的自旋策略。已有日志里，ADAPT、B1000、B5000 三个候选最终都没有通过预设验收条件。其中 B1000 在一个中负载场景中比更优基线慢约 13%，超过了允许的退化门槛。

因此，这一方向应记为“尝试后未通过验收”。只挑出有改善的场景，会漏掉决定是否保留改动的退化项。

后续候选只移植日志无损打包

随后留下的候选集中在日志无损打包，本地源码中已有 vecpack.h 及相关存储、引擎文件。项目记录限定了这次移植的范围，没有把此前其他分支的距离求和、排序等改动一并带入。

正确性方面，当天保存的执行日志包括：

  • 33,005 个向量的按位往返检查，多个编译及检测配置通过；
  • 协议测试、日志输出对比和查询差分检查通过；
  • 包含重启、强制终止后恢复的测试；
  • 在 128 MiB 限制下加载 300,000 行，恢复后核对通过。

移植过程中还保留了一个旧分支的失败用例：恢复后的查询错误地返回空行，而参考结果应有两行。后续候选的记录显示，这个回归用例通过了检查。它说明测试覆盖了这个具体问题，不能据此推断所有持久化问题都已解决。

以上是当天已有日志记录的运行结果，并非整理这篇文章时重新运行的测试。

主要收益落在 I/O 和内存

候选 P 与基线 A 做了两组各 12 轮的本地配对比较。完整精度数据和 6 位小数数据的答案摘要分别一致；每组实验中，写入与查询统计的 I/O 字节量都下降，内存指标也下降。

不过，耗时结果还不足以支持“稳定提速”。例如，完整精度数据的写入耗时比 P/A 为 0.966，95% 区间为 [0.938, 1.031]；查询为 1.015，区间为 [0.923, 1.048]。两个区间都包含 1，方向并不稳定。6 位小数数据的耗时比较也有同样的限制。

因此，目前适合记录的结论是：本地测试支持日志打包候选降低 I/O 和内存开销，尚未证实耗时稳定改善。 报告中的校准评分采用了假设基线，不能当作平台实测分数。
